Developers · v9.0.0 · Skill Marketplace & Workflow SDK

技能市场开发者文档

面向往技能市场发布内容或接入 Claude Code 技能的开发者：市场里有什么、内容长什么样、怎么被校验与分发、 客户端拿到之后会做什么。作者侧的逐字段写作规范在内容仓库里（见下方「内容仓库」）， 这里讲的是客户端契约、Claude Code 技能规范支持与交付链路——那部分只有在应用侧才能看到。

用户视角怎么用市场，见使用手册 §5.7 技能市场。

相关的客户端实现：src/main/agent/（v9.0 进程内 Pi Agent 运行时、原生 skill 工具、load_toolset 按需工具集引擎与 piSessionStore.ts 无锁 JSON 会话存储）、 src/shared/claudeSkill.ts（Claude Code 技能规范与 frontmatter 解析）、 src/main/services/claudeSkillRuntime.ts（变量展开、!`cmd` 预处理、hooks / fork 子代理 / allowed-tools 治理）、 src/main/services/githubSkillInstaller.ts（GitHub 技能直装）、 src/shared/graph/nodeCapabilities.ts（画布节点原生能力定义）、 src/shared/skillMarket.ts（契约与解析）、 src/main/services/marketPipeline.ts（下载 / 缓存 / 原子安装）、 src/main/services/skillMarketService.ts（目录、兼容性、安装记账）、 src/renderer/src/views/MarketplaceView.vue（界面）。

1. 市场里有什么

技能市场是一个独立窗口（顶栏「技能市场」按钮打开，紧挨「设置」左边），分三个页签：

页签 内容 托管位置
全部 MCP 服务与全部技能混排展示，支持搜索与顶部 GitHub 技能直装 —
MCP 内置 aiartengine 工具服务、Blender 工具面，以及用户自己添加的第三方 MCP 服务（http / stdio） 应用内 + 用户本地配置
技能 官方/社区市场技能（可附带 workflow.json 画布模板）、GitHub 直装技能、项目级技能（.claude/skills / .agents/skills）、自定义技能 内容仓库 + GitHub 任意仓库 + 工作区 + <userData>/dsh-harness/skills

为什么只有三个页签、且不再有「内置节点技能」？

  • 内置技能已重构为画布节点原生能力：旧版曾把 40+ 个画布节点的默认系统提示词与用法写成 .md 文件铺在 <userData>/dsh-harness/skills/ 下。重构后，节点的生成能力（defaultSystemPrompt、usage、inputBindings 等）全部收归为节点自身定义（src/shared/graph/nodeCapabilities.ts），由 MCP graph_node_types 直接向 Agent 暴露，不再混入技能目录。
  • 工作流与技能合流为「技能」页签：远端市场仓库里的条目本质上是「给 Agent 看的操作手册（SKILL.md）+ 可选的一键工作流画布模板（workflow.json）」。安装后，条目既能在画布「新建 → 一键工作流」里复现节点图，也会把技能包落盘到 <userData>/dsh-harness/skills/<skill.name>/（由进程内 Pi Agent 的原生 skill 工具无缝发现与加载），在「技能」页签中统一管理（不重复渲染两张卡片）。

内容仓库

  • 主源：https://github.com/Justin-sky/ai-art-engine-skills（raw 路径 /main）
  • 镜像：https://gitee.com/beijing_blue_whale_era_zhangjian/ai-art-engine-skills（raw 路径 /main）

两个仓库的内容必须逐字节一致——不一致会造成「同一版本号、不同内容」， 这是最难排查的一类状态。同步方式见仓库 README。

作者侧的字段规范、审核标准、逐条拒绝原因在内容仓库的 CONTRIBUTING.md； 目录结构、workflow.json 各字段含义在同仓库 README.md。 这里不重复那份规范，只讲它没覆盖的客户端行为。

2. 交付链路：一步都不能省

贡献者提交 workflows/<id>/{workflow.json, cover.png, skill/**}
   ↓  CI 校验（validate.mjs + 单测）
   ↓  build-index.mjs 从磁盘派生 index.json（含技能文件清单）
客户端拉 index.json（先主源，失败降级镜像）
   ↓  用户点「安装」
下载 workflow.json + cover.png（+ 技能文件）
   ↓  原子安装（staging → rename，失败不留半成品）
<userData>/workflows/<id>/            画布模板本体
   ↓  同一次安装内
<userData>/dsh-harness/skills/<skill.name>/   技能包（随条目一起落盘，无缝兼容旧版路径）
   ↓
进程内 Pi Agent 扫描发现该技能 → 注入 <available_skills> → 原生 skill 工具按需加载 / 斜杠调用

2.0 单一事实源：核心精简内置 + 独立 ai-art-engine-skills 仓库分发

垂直领域工作流预设已全面迁出客户端主仓库，统一收归独立的开源仓库 ai-art-engine-skills 作为单一事实源（早期主仓库内的预设双份镜像与旧版同步导出脚本已随架构迁移一并移除，彻底根绝「客户端与市场同名不同图」的版本漂移）：

  • 客户端核心内置预设：应用本体（src/renderer/src/features/aiWorkflow/presets.ts）仅内置最精简的离线核心预设 builtin.video-breakdown-remake（semantic.analyze → semantic.rebuild 两节点视频拆解与 1:1 复刻）。
  • 官方与社区领域技能及工作流：短剧漫剧（short-drama）、游戏量产、电商海报、有声小说、3D 资产等全部官方与社区领域包均托管在独立仓库 ai-art-engine-skills（标准布局为 skills/<slug>/SKILL.md + workflows/<slug>.aiae-workflow.json，以及聚合目录 workflows/<id>/{workflow.json, cover.png, skill/**}）。
  • UI 与 MCP 全链路安装调用：用户和 Agent 既可在顶栏技能市场（Skill Marketplace）窗口一键搜索安装，也可直接通过 6 个原生 MCP 工具完成检索、审查、安装与画布实例化：skill_list、skill_search、skill_inspect_github、skill_install、skill_uninstall 与 workflow_use_installed（参见 MCP 接入指南）。
  • 作者如何导出发布新工作流：在自由画布搭好并跑通节点图后，右键选择「导出为市场工作流」（或导出带 aiae:graph 块的 PNG 配方图），填写元数据与封面即可生成标准包（requires.nodeTypes 自动从 plan 派生，运行时临时写回字段自动剥离）；随后在 ai-art-engine-skills 仓库内执行 node scripts/build-index.mjs && node scripts/validate.mjs 即可提交 PR。

2.1 索引里的派生字段由脚本生成，贡献者不要手写

index.json 里这些字段全部由 scripts/build-index.mjs 从磁盘派生：

  • requires.nodeTypes（该工作流用到哪些节点类型）、requires.appMinVersion
  • nodeCount / edgeCount / sizeBytes
  • skill：技能包的名字、描述、是否含脚本、文件清单、整包体积

最后一项尤其关键，原因值得写下来：

raw 源没有目录列表 API。客户端必须先知道每个文件的路径才能逐个下载， 所以技能包的文件清单只能由服务端（仓库脚本）派生。把清单交给脚本从磁盘生成， 就不可能出现「清单与磁盘漂移」——而这正是手写清单必然发生的故障。

workflow.json 里不写技能文件清单，只靠「skill/SKILL.md 是否存在」这一事实作为声明。CI 会比对索引与磁盘派生结果，手改索引会被拒。

2.2 市场附带画布模板的技能包为什么要带 wf- 前缀

技能包落地目录是 <userData>/dsh-harness/skills/<name>，与用户从 GitHub 直装的 Claude Code 技能、本地自定义技能共享同一个目录。 因此，ai-art-engine-skills 仓库里随画布模板分发的技能包强制将 name 命名为 wf-<工作流 id>，从源头避免与通用 Claude Code 技能重名。仓库校验器逐条拦这件事。

2.3 技能包文件布局

workflows/<id>/skill/              # 或独立技能布局 skills/<slug>/ + workflows/<slug>.aiae-workflow.json
  SKILL.md          必需。frontmatter: name(wf-<id>) / description / workflow: <id>
  references/       可选。端口与参数速查、长契约、示例
  scripts/          可选。见 §4
  assets/           可选
  examples/         可选（GitHub 直装 Claude Code 技能同样支持）
  templates/        可选（GitHub 直装 Claude Code 技能同样支持）
  • 只允许上面列出的标准子目录；不允许符号链接。
  • 单文件 ≤ 128KB，整包 ≤ 512KB，文件数 ≤ 40（客户端逐个下载，不能没有天花板）。
  • description ≤ 500 字符：技能目录会截断它，而它是 Agent 决定是否加载这份技能之前唯一能看到的东西——请写成「什么时候该加载它」，而不是功能罗列。

2.4 工作流预设与技能正文中的合法节点命名空间（v9.0.0）

仓库校验器会严格校验工作流预设 plan 及技能正文里反引号包裹的 x.y 节点类型记号。v9.0.0 允许使用的 18 个标准画布节点命名空间如下： 

input.*     text.*      image.*     video.*     voice.*     audio.*
film.*      game.*      ui.*        novel.*     semantic.*  script.*
stage.*     director.*  model3d.*   world.*     gameplay.*  output.*

凡落入上述已知节点命名空间的 x.y 记号，必须是客户端 graph_node_types 注册表中真实存在的节点 typeId。

为什么值得单独一条：技能是写给 Agent 的操作手册，它会照着里面的 typeId 去调用 graph_edit 建图。编造一个不存在的类型（如 image.pic 之类），Agent 就会写出一张无法执行的残图。 按命名空间过滤是为了不误伤 cover.png / references/ports.md / SKILL.md 这类文件名写法。 节点参数名请单独用反引号写（如 generateAspectRatio），不要写成 type.param 的点号形式。

2.5 Claude Code 技能规范支持与 GitHub 直装

除了从官方 ai-art-engine-skills 市场安装外，客户端完整支持 Claude Code Skill (SKILL.md) 规范，并允许直接输入任意 GitHub 地址安装：

  • GitHub 地址直装（githubSkillInstaller.ts）：在技能市场顶部的 GitHub 安装栏可直接输入 owner/repo、https://github.com/owner/repo、https://github.com/owner/repo/tree/<branch>/<subpath> 或 .../blob/<branch>/<subpath>/SKILL.md。安装器通过 GitHub Tree API 获取文件清单，校验单文件/总包体积与子目录白名单，若含 scripts/ 则复用 §4 的脚本同意流；落盘后写入 .source.json 记录源仓库、分支、子路径与 commit SHA，支持在技能卡片上一键从 GitHub 更新或卸载。
  • 多级技能发现作用域：项目级（<workspace>/.claude/skills/<name>/SKILL.md、<workspace>/.agents/skills/<name>/SKILL.md，优先级最高）> 个人/市场级（<userData>/dsh-harness/skills/<name>/SKILL.md）。
  • Frontmatter 全字段支持（claudeSkill.ts）：支持 name、description、argument-hint、disable-model-invocation、user-invocable、allowed-tools（支持 Bash(git *) 等通配模式）、model、context: inline | fork（fork 在独立子代理上下文中运行技能）、agent、hooks（PreToolUse / PostToolUse / Stop）、when_to_use、version、license、author、workflow。
  • 参数替换与动态上下文注入（claudeSkillRuntime.ts）：支持 $ARGUMENTS、$ARGUMENTS[n]、$0..$9 位置参数，以及 ${CLAUDE_SKILL_DIR}、${CLAUDE_SESSION_ID}、${WORKSPACE_ROOT}；正文中形如 !`command` 的标记会在技能加载前执行预处理命令（受用户审批约束）并内联替换输出。

3. 客户端安装契约

3.1 卡片与动作

在市场的技能（及全部）页签中，顶部提供 GitHub 技能直装栏与本地技能管理动作（打开目录 / 生成示例模板 / 导入自定义技能）。 远端市场条目卡片上直接有 安装 / 更新 / 重新安装 / 卸载 与 详情，不必先进详情页。 卡片徽标会显示 含技能 或 含技能 · 含脚本——装之前就让用户知道 Agent 那边会多拿到一份手册（含脚本时更要说清）。

已安装的市场条目直接在原卡片上展示「已安装」状态与管理按钮（不会在技能列表中重复出现第二张卡片）；GitHub 直装技能、项目级技能（.claude/skills）与个人自定义技能则以独立技能卡片列出，支持查看详情、更新或移除。

3.2 原子性与回滚

安装走 marketPipeline：先下到 staging，全部就位后再 rename 换入，失败清理。 技能包与工作流本体同生共死：技能装失败（或校验不通过）会把工作流本体一并卸掉并返回 失败原因。理由很直接——卡片写着「含技能」而技能没落地，等于界面在骗人； 安装是幂等的，重试即可。

3.3 安装前校验（否则「装上了却看不见」）

Pi Agent 运行时在扫描技能目录时会对不合法的 SKILL.md 自动跳过（仅写告警日志而不挂载）。所以客户端在 staging 阶段就校验 SKILL.md：frontmatter 是否存在、name 是否合法、 description 是否非空、字段类型是否符合 Claude Code 技能规范。不通过就安装失败并给出具体原因，绝不会留下一个装了却不生效的技能包。

3.4 卸装

卸载市场工作流条目会连带删除它装上的那个技能包——只按记账里记着的那一个目录名删， 绝不按前缀批量删（用户可能自建了同名技能）。通过 GitHub 直装或本地导入的独立技能，可在卡片上直接点「卸载」移除对应技能目录。

3.5 目录刷新

打开市场窗口即强制刷新目录（这样往仓库推了新内容，重开窗口就能看到，不必等缓存 TTL）。 刷新失败但手上已有内容时保留旧列表并给软提示，不用错误顶掉已有内容。 缓存按源分别落盘：主源与镜像各存一份，避免把镜像的缓存当成主源的数据。

4. 脚本（scripts/）与同意流

技能包可以带脚本，但默认不装：它属于「会在用户机器上运行的代码」， 必须由用户明示同意。

4.1 安装时：每次都要问

  • 含脚本时，安装前弹出确认框，逐条列出脚本路径，并说明这是 Agent 可以在本机运行的代码。
  • 确定 = 写入脚本；取消 = 只装 SKILL.md 与 references/（技能与工作流照常可用）。
  • 每次安装 / 重新安装都会再问一次，不记住同意——同意是每次安装的独立决定， 不是一个装过一次就永久生效的开关。
  • 主进程只认字面量 skillScriptsConsent === true，不做真值 coercion。
  • 脚本文件同样受路径白名单与体积上限约束。

4.2 运行时：实时沙箱与单次失效关闭（Fail-Closed）审批卡

内置 Pi Agent 真正去跑脚本时，走的是原生跨平台终端工具（Windows 上默认 pwsh / PowerShell）， 受实时沙箱约束（默认处于 🛡️ 受限模式 / workspace-write，用户也可在对话底栏实时切换为 🔓 完全访问 / danger-full-access）。在受限模式下，一旦某一步需要越出工作区沙箱或执行敏感命令，就由对话内权限审批卡把决定权交给用户：

用户选择 结果
允许一次（Allow Once） 仅该次调用单次放行（令牌用后即焚）
始终允许（Always Allow · 项目作用域） 仅在当前工程作用域内对该类受控操作放行（跨工程隔离，不污染全局）
拒绝（Reject） 工具调用被拒
无人应答 / 超时 / 载荷读不懂 / 读文件出错 / 任何异常 失效即关闭（Fail-Closed）（工具调用失败，绝不放行）
请求被中止（本轮结束） 取消，不放行

界面上是一张对话内授权卡：清晰展示工具名、命令与风险原因，提供 允许一次 / 始终允许（仅限当前项目）/ 拒绝，任何未显式授权的异常分支一律拒绝执行。

写技能时请据此设计：脚本必须是可选的。用户拒绝脚本时，仅凭说明与 references 也要能用；不要把关键步骤只放在脚本里。

5. 可执行代码节点（script.run）与同意流

§4 讲的是技能包里的脚本（skill/scripts/，给 AI agent 在本机跑的文件）。 这一节讲的是另一条、互相独立的路径：工作流本体 plan 里的可执行代码。

script.run 是一种节点类型，代码（JavaScript）作为它的参数写在 plan 里， 由应用的图执行引擎在渲染进程里跑——而不是 Agent 的本机终端。它运行在 受限沙箱（QuickJS WASM，src/shared/graph/execute/scriptSandboxQuickjs.ts）里： 无文件、无网络、无 require、无宿主全局。沙箱与应用之间只有三样东西过得去—— 上游输入进、端口输出出，以及一组 await om.<能力>(...) 的受控能力调用： <能力> 必须在该节点的 capabilities 白名单里声明过，每个 om.* 都转发到应用治理过的能力（提供商 / 密钥 / 配额 / 日志），不是后门。再叠加超时（deadline 中断）与内存上限。

5.1 识别与派生（仓库侧 + 客户端同口径）

  • 仓库 build-index.mjs 从 plan 派生 hasExecutableCode: true 与逐条脚本摘要（节点 key / 标题 / 声明用到的能力 / 代码字符数 / 短 hash）写进 index.json；贡献者不手写这些字段（与 requires.nodeTypes、技能清单同理）。
  • 客户端 parseSkillMarketEntry / parseWorkflowBundle 认这些字段并再校验一遍。
  • 校验器对每个 script.run 节点核对边界：code 非空且 < 100000 字符、 capabilities 只能取白名单内的能力、端口 id 合法不重名、limits 不超硬顶 （timeout ≤ 120s、mem ≤ 512MB）。代码为空 / 超长这类无法规整的会拒绝整条工作流 （代码是工作流的一部分，不像坏技能能降级丢弃）；越白名单的能力、超硬顶的资源会被就地规整 （丢弃 / 夹到上限），不致整体拒绝。

5.2 安装时：含代码必须逐次同意，拒绝即不导入

  • 含 script.run 的工作流卡片标 含可执行代码（与技能的「含脚本」区分开）。
  • 安装前弹确认框，逐条列出每个脚本节点声明用到的能力与代码规模。
  • 确定 = 安装并允许运行；取消 = 不安装这条工作流—— 这与技能脚本的「取消只跳过脚本、照装其余」不同，因为代码就是工作流的一部分，去掉它工作流不成立。
  • 每次安装都重新问、不记忆、无「总是允许」。主进程只认字面量 scriptConsent === true。
  • 本地自建豁免：用户自己在应用里创建 / 编辑的脚本节点不走市场同意流（本来就是本人写的）， 只有从市场导入才拦。
与技能脚本的关系：两条路径各自独立同意。一条工作流可能既「含技能 · 含脚本」又「含可执行代码」， 届时两个确认框各问各的。

6. 兼容性与版本

  • 索引 schemaVersion 目前是 1；比客户端更新的索引会让客户端明确报「请先更新应用」， 而不是半渲染出一个误导性的空市场。
  • 条目可声明 requires.appMinVersion：应用版本低于它时卡片会被禁用并给出原因。
  • requires.nodeTypes 由脚本从 plan 派生：旧版应用缺某个节点类型时会提前判定并在安装前提示， 而不是等物化时才落出一张残图。
  • 同内容必须升版本：同一 version 的内容不得再改。

7. 本地调试

7.1 在内容仓库里

node scripts/validate.mjs          # 格式 / 依赖 / 索引一致性 / 技能包全部规则
node scripts/build-index.mjs       # 重建 index.json（派生字段）
node scripts/build-index.mjs --check   # CI 用：索引是否与磁盘一致
node --test scripts/validate.test.mjs  # 校验器自身的单测

validate.mjs 与 CI 跑的是同一份代码——本地过、CI 不过这种事不该发生。

7.2 在应用侧

  • 自建源：数据层支持把 skillMarket.source 设成一个或多个地址 （空白 / 逗号分隔；填了就只用填的，不混入官方源，避免回退把排查带偏）。 ⚠️ 当前设置界面还没有暴露这个输入项，属于数据层能力。
  • 想验证「Agent 到底有没有真的加载技能」，最可靠的证据是内置 Pi Agent 的无锁原子 JSON 会话文件 （<userData>/dsh-harness/pi-sessions/<sessionId>.json，由 piSessionStore.ts 维护）： 直接打开该明文 JSON 即可查到原生 skill 工具调用记录（name: "skill"、参数 {"name": "<skill-name>"}） 及紧随其后注入的技能正文内容（或直接把会话导出为 .zip 检查）。别只看回复文案——技能是否被真正加载，看会话工具调用记录最准确。

8. 常见退回原因（客户端视角）

除内容仓库 CONTRIBUTING.md 列的那些之外，这几条会直接导致装上了却不生效：

现象 原因
装完 Agent 那边没有这份技能 SKILL.md 的 frontmatter 不合法（Pi Agent 扫描技能目录时自动跳过不合法条目）。客户端的安装前校验 就是为了把这种失败提前成一句可读的报错
市场工作流技能包校验被拒 附带画布模板的仓库技能包 name 没带 wf- 前缀
描述在 Agent 那里被截断 description 超过 500 字符
更新后文件对不上 手改了 index.json；它必须由 build-index.mjs 派生
技能里写的节点类型建不出图 正文里出现了不存在的 typeId（仓库校验器会拦，但改写正文后请重跑）
用户拒绝脚本后功能不可用 技能把关键步骤只写在 scripts/ 里；脚本必须是可选的
